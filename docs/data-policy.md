# 記事データ・一覧取得・収集の方針

更新日：2026-10-09

[READMEに戻る](../README.md) · [ルール](rules.md) · [技術構成](architecture.md)

Issue #3で決めた設計。設定画面・収集・DB処理の実装済み機能を示すものではない。

## 記事の識別と日時

- 共通記事データに取得元の識別情報を持つ。表示用のサイト名とは分ける。
- 取得元は設定されたフィードURL、YouTubeのチャンネル、Podcastのフィード、GitHubのリポジトリを区別する固定キーとする。同じ取得先の設定を重複作成しても別の取得元にはしない。
- 同一記事は「取得元＋外部記事ID」で判定する。記事IDが取得できなければ「取得元＋URLの完全一致」で判定する。IDとURLはキーの種類を区別する。
- URLから追跡パラメータを取り除くなどの正規化は行わない。異なる取得元をまたいだ記事の統合も行わない。
- 途中で記事IDの有無が変わる場合の照合・移行処理は設けない。必要になった段階で取得処理を見直す。
- DB内の記事IDは外部記事IDとは別に、単調増加する整数を割り当てる。照合キーに一意制約を設ける。
- 取得日時は最初にDBへ取り込んだ時点で固定する。再取得しても表示位置や保持期限を延ばさない。削除後に再取得された記事には新しい取得日時とDB内の記事IDを割り当てる。
- 公開日時・掲載元の更新日時は取得日時とは別に持ち、再取得時は提供された値で更新する。更新日時を公開日時と区別できない場合は公開日時を更新する。既読・気になる・ピン止めは維持する。
- 保存する日時はUTCで統一する。日本時間の収集予定・日付の区切りはAsia/Tokyoで計算する。

## 一覧の分割取得

- 全記事・気になる一覧は一回20件を取得する。
- 並び順は取得日時の降順、同時刻はDB内の記事IDの降順とする。仕分け対象の選択にも同じ順序を使う。
- カーソルは最後に返した記事の取得日時とDB内の記事IDを表す。次のページはこの組より後ろの記事を取得する。件数による位置指定は使わない。
- 次のページの有無は一件多く検索して判定し、返す記事は最大20件とする。対象記事が削除されてもカーソルの値で続きを指定できる。
- スクロール中に先頭側へ追加された新着は自動挿入しない。下に引く更新で先頭から読み直す。
- 各ページは取得時点のDBの状態を返す。閲覧開始時の全件スナップショットは保持しない。途中削除された記事や、気になる条件が変わった記事が、閲覧中の一覧に完全に揃うことは保証しない。一覧更新で最新状態へ揃える。
- フロントは記事IDで重複を除く。一覧切り替え・更新前の古い要求への応答を反映しない。保存中の操作との整合はIssue #4で決める。

## 初期設定

| 設定 | 初期値 |
|---|---|
| 収集予定 | 毎日午前5時、Asia/Tokyo |
| 各取得先の確認件数 | 最新側から最大50件 |
| 未読・保護なしの記事の保持期限 | 最初の取得日時から30日（30×24時間） |
| DB全体の記事件数上限 | 10,000件 |
| 一覧の一回の取得件数 | 20件 |
| 一回の仕分け対象数 | 最大10件 |

収集時刻・取得件数・保持期限・件数上限は変更可能な設定として実装する。まず検証するための初期値であり、最適な数値や新着件数の保証ではない。気になる・ピン止めは自動削除から保護し、既読は期限では削除しない。件数超過時は保護なしの未読を取得日時が古い順、続いて保護なしの既読を最後に開いた日時が古い順に削除する。同時刻はDB内の記事IDの昇順で固定する。

## 対応情報源とデフォルト取得先

ユーザーが取得先を追加・変更・無効化できる方針とする。初期登録する取得先は、既存の調査スクリプトで扱った次の5件とする。RSS・Atomでは任意の対応フィード、YouTubeではチャンネル、GitHubではリポジトリを設定する。任意のAPIを設定だけで扱う仕組みは作らず、APIごとの対応Adapterを用意する。

| 情報源 | デフォルト取得先 | 方法 |
|---|---|---|
| Zenn | https://zenn.dev/feed | RSS |
| Cloudflare Changelog | https://developers.cloudflare.com/changelog/rss/index.xml | RSS |
| YouTube / Google Developers | https://www.youtube.com/feeds/videos.xml?channel_id=UC_x5XG1OV2P6uZZ5FSM9Ttw | Atom |
| Podcast / Syntax | https://feed.syntax.fm/rss | RSS |
| GitHub Releases / cloudflare/workers-sdk | https://api.github.com/repos/cloudflare/workers-sdk/releases | GitHub API |

最新最大50件には既存記事も含まれる。新規だけ追加し、既存は更新する。提供件数が50件未満ならその範囲を扱い、日々250件の新着を保証するものではない。フィードが提供しない過去記事を補完しない。GitHub Releasesは公開リリース（プレリリースを含む）を公開日時の新しい側から最大50件確認する。APIの既定順序だけを新着順と仮定せず、対応実装で確認する。取りこぼしは許容する。

取得先の設定UI・APIは後続作業として切り分ける。収集の実装では固定サンプルと本番のSourceConfigを区別する。デフォルトは検証用に幅広い種類を含めており、利用量に応じてユーザーが無効化できる。

2026-10-09にRSS・Atomの4取得先でHTTP 200とXMLの解析を確認した。提供件数はZenn 20件、Cloudflare Changelog 1,320件、YouTube 15件、Syntax 1,045件だった。これはフィード全体の掲載件数であり、一日の新着数ではない。GitHub Releasesの公開APIも応答を確認した。取得処理を実装するときにも仕様と取得順を確認する。

## 収集・保持の実行単位

- 単一VM・単一Nestプロセスで定期収集する。実行中に次の予定時刻を迎えたら、その回はスキップする。完了・失敗にかかわらず実行中フラグを解除する。
- 取得先は順に処理する。一つの取得先の通信・解析が失敗しても他の取得先を続ける。収集失敗の履歴をDBへ保存する機能は設けず、その取得先は次の予定時刻に再び取得する。
- 必須情報がなく変換できない一件は追加せず、残りを処理する。説明・公開日時の欠損は除外理由にしない。
- 収集開始時に期限・件数整理を行う。既存更新は記事単位で保存し、新規追加は期限整理・追加可否の確認・追加・件数整理を一つの短いDBトランザクションで保存する。
- 外部通信中はDBトランザクションを保持しない。削除候補の判定と削除は同じトランザクション内で行い、保存済みの保護状態を確認する。照合キーの一意制約で重複を防ぐ。
- DB保存が失敗した単位はロールバックし、成功とは扱わない。DB処理の継続が不可能ならその回を終了する。成功済みの記事は維持し、次の収集で再確認する。登録・既読・未送信結果の失敗時操作はIssue #4の範囲とする。
- 保護記事だけで上限に達した場合は新規追加を止める。取得範囲内の既存記事の更新は続け、次の収集で追加可否を再判定する。

## 毎日の自動仕分け

毎日の初回起動時に対象があれば最大10件の仕分けを自動で開始する。日本時間の午前0時を日付の区切りとし、その後はユーザーが自由に仕分けを開始できる。収集完了が仕分けを自動的に起動するわけではない。

起動時の未送信登録の同期がある場合は、同期完了後に自動開始を判定する。対象0件なら空の回を開始せず一覧へ進む。日次判定の記録先、初回起動で対象0件だった場合の扱い、複数端末の扱いは、起動・操作仕様を扱うIssue #4で具体化する。
