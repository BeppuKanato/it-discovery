# 操作・同期・失敗時の方針（Issue #4）

2026-10-15の合意に基づく操作仕様。後続Issueへ渡す基準とし、機能の実装済みを意味しない。再試行間隔・識別子などは、合意した動作を満たすための設計上の初期値とする。

## 2026-10-20の変更：一覧・既読の永続再送を廃止

この節を、以下の旧方針のうち一覧・既読に関する記述より優先する。

- ピン・気になるは通信中の表示と関連操作の制限を行い、保存成功後に状態を確定する。明確な失敗は元の表示と通知、結果不明はその旨を案内し、現在状態の取得で確認する。
- 既読は外部を開く処理を待たせず送信するが、永続キュー・次回起動時の再送は行わない。
- 一覧・既読のoperationId・操作結果記録・結果照会は廃止する。これらの未送信解消を初回一覧取得の条件としない。
- 仕分けの途中結果の端末保存、batchId＋revisionによる再送・重複防止は維持する。仕分け結果が残った場合の起動待機も今回変更しない。
- バックエンドとフロントを直接保存へ接続した。一覧の端末キュー・起動待機は撤去済み。結果不明時は一回GETし、取得不能なら更新を止めて手動確認を案内する。[一覧操作](article-list-state.md)と[新API](article-state-api.md)を参照。旧ブラウザ記録を勝手に削除・再送しない。
- 仕分けフロントの端末保存・起動統合は後続Issueの仕様で、実装済みを意味しない。

## 合意済み：外部記事と既読

既読は「新しい外部タブの作成と遷移依頼を受け付けた時点」で記録する。タブ作成の拒否、URL不正、遷移依頼時の例外を検知した場合は既読にしない。外部サイトの通信エラー、404、認証要求、本文の表示完了や読了は判定しない。既読保存は非同期とし、外部への移動を待たせない。

別オリジンの本文をアプリ側で読むことはSame-origin policyで制限される。`window.open(url, '_blank', 'noopener')`は作成成功でもnullを返すため、nullだけで拒否と判定しない。[Window.open](https://developer.mozilla.org/en-US/docs/Web/API/Window/open)・[Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)を参照。

実装候補は次の順序とする。

1. URLがhttp(s)であることを確認する。
2. クリック処理の中で、awaitを挟まずabout:blankの新規タブを作る。
3. 参照がnullなら受付失敗とする。
4. 空タブのopenerをnullにし、元画面への参照を切ったことを確認する。
5. 空タブへ元記事URLの遷移を依頼する。ここまで例外がなければ受付成功とする。
6. 既読保存を別に依頼する。本文の応答を成功判定に使わない。

この順序が使えない環境で、単にリンクをクリックしただけで成功と推定する代替動作は入れない。元画面へ戻ったときのカードは同じ記事のままとする。

## 確定：仕分けの操作

- 一覧へ移動する機能は設けず、途中でも「仕分けを終了する」でそこまでの判断を確定する。
- 元記事から同じカードに戻り、既読カードは「次へ」で進める。10件のうち1件として数え、気になる状態を変えない。
- 開始時に選んだ最大10件のカード情報と順番を手元で固定する。収集で新着が増えても割り込ませない。
- 戻す操作は終了の確定前まで可能。既読を戻すことはしない。「次へ」の進行も戻れるようにする。
- サーバーで削除されたカードがあっても表示だけは手元に残り得る。登録送信時は再作成せず、その記事が削除済みであることを返す。

## 確定：端末保存と送信中の操作

- 端末保存は順番どおり処理する。失敗を検知した時点で判断・戻す操作を停止し、最後の手元の結果を保って再試行または終了を選べるようにする。未保存のまま閉じると失われる変更があることを知らせる。
- 終了時は端末への最新結果の保存を待つ。送信開始後は判断・戻すを止め、送信対象を固定する。
- 一時エラーや応答不明は同じ識別情報で再送する。通信待ちは1・2・4・8・16・30秒と間隔を広げ、その後30秒間隔。オフライン中は連打せず復帰を待つ。終了しても端末の未送信結果は消さない。
- 起動時は未送信結果の同期が済むまで一覧と仕分けを待機する。ブラウザのタブをアプリから必ず閉じられるとは限らないため、「終了」は通常操作を開放しない終了画面とし、利用者自身でもタブを閉じられる。

## 確定：再送と恒久エラー

- 仕分け結果はbatchIdとrevision、一覧変更はoperationIdで識別する。同じ要求の内容は再送時に変えない。
- サーバーは識別情報と処理結果を変更と同じトランザクションで保存し、同じ要求の再送には同じ結果を返す。処理済みなら後の解除を古い再送で登録に戻さない。
- 初期実装では処理済み要求の識別情報・内容の照合情報・結果をサーバーへ保持し、自動期限削除は行わない。短期間で消して古い再送を再実行しない。将来整理を追加する場合は古い要求を再実行しない規約も合わせて設計する。
- 一括登録は記事ごとに「保存済み／削除済み」を返し、その回の有効な登録と結果記録をまとめて保存する。削除済みだけを理由に残りを永久待機させない。削除済みの結果を利用者へ知らせてから、その項目の未送信結果を解消する。
- 不正な要求は自動再試行を止め、更新・再起動または対象の未送信変更の明示的な破棄を案内する。認証失敗は本人確認の復旧へ案内し、破棄以外では未送信結果を残す。DB障害・容量不足は運用側で復旧してから再試行する。

## 確定：一覧の連続操作と既読

- 一覧の気になる・ピン・既読の未送信変更も端末へ残す。画面は即時反映し、端末保存と通信は非同期に行う。端末保存失敗なら該当の状態変更操作を止め、再試行を案内する。
- 同じ記事の保存要求は直列化し、先行要求が確定するまで後続要求を送らない。画面は最新の希望状態を示す。異なる記事は独立して扱える。
- 設定値を指定して保存し、トグル要求を再送しない。応答不明はoperationIdの処理結果を確認する。現在の記事状態だけで先行要求が未実行と断定しない。
- 一覧を再取得しても未確定の希望状態を重ね、古いDB状態で画面を戻さない。保存しなかったと確定した操作だけを解消し、後続の希望があれば残す。
- 既読は開いた日時を保存し、古い送信で最後に開いた日時を巻き戻さない。

## 確定：日次判定と端末

- 日次の自動仕分けは端末ごとに日本時間の日付を端末へ保存する。対象0件でもその日は判定済みとし、その後は手動開始できる。
- 判定の取得失敗は判定済みにせず再試行できる。端末の日次記録に失敗したら自動再開始を繰り返さず、通知して手動開始へ案内する。
- 日付は午前0時で切り替わるが、開きっぱなしの画面で突然開始しない。起動処理時にだけ判定する。
- 日次の判定は端末ごとに行う。初期の動作保証は本人が一度に一つの端末を操作する範囲とする。同じブラウザの複数タブは送信の所有権を一つにし、別端末間の同時操作はOPEN-08の別途検討範囲とする。

## 再送プロトコルの境界

- 仕分けは送信対象を固定したbatchId＋revision、一覧・既読は端末で作ったoperationIdを送る。識別子は端末保存してからサーバーへ送信する。同じ識別子で違う内容を送った場合は競合として拒否する。
- 応答は識別子と記事ごとの保存結果を含む。削除済みは再作成しない恒久結果とする。DB障害では変更と処理結果を共にロールバックし、一部だけ成功したという応答を作らない。
- 応答不明時は同じ識別子の処理結果を照会する。結果未記録だけでは古い要求の失敗と断定せず、同じ要求を再送する。処理中または再送の競合は直列化し、一つの結果に確定する。
- 端末は応答の識別子・版が一致した記録だけを消す。サーバー成功後に端末削除が失敗した場合も、再送は保存済みの同じ結果になり、後の解除を巻き戻さない。
- 一覧の再取得は未確定の変更を上書きしない。起動時は仕分け・一覧・既読の未送信を同期してから日次判定へ進む。同じ記事の既読と登録は送信順を保つ。
