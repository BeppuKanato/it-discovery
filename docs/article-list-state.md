# 一覧の気になる・ピン操作

[README](../README.md) · [構成とコードの読む順序](frontend-architecture.md) · [状態変更API](article-state-api.md)

2026-10-20の変更後の仕様。全記事・気になる一覧でピン・気になるを登録・解除する。永続再送は行わず、保存中の表示と操作制限を行う。元記事を開く・既読保存は[共通処理](article-opening.md)で接続済み。

## 操作と失敗時の動作

| 場面 | 動作 |
|---|---|
| ボタンを押す | 現在値を反転した値をPUTする。登録状態は成功まで変えない |
| 保存中 | 対象アイコンを固定の部分着色にし、同じ記事の二つの変更ボタンを止める。スピナーは使わない |
| 別の記事 | 独立して操作できる |
| 保存成功 | サーバーが返した状態をVMのarticlesへ反映する |
| 気になる一覧で解除成功 | 対象記事を表示から除く。続きがあれば引き続き取得できる |
| 400・401・403・409・422 | 元の状態を保持し、カード下へ受け付けられなかった旨を表示する |
| 404 | 記事を除き、削除済み通知を表示する |
| 500・429・ネットワーク障害・タイムアウト・壊れた応答 | PUTを再送せず、GETで現在状態を一回確認する |
| 現在状態の確認成功 | 現在の値へ表示を合わせ、確認した旨を表示する |
| 現在状態の確認失敗 | 元の表示を残し、同じ記事の更新を止めて「状態を確認」を表示する |
| 「状態を確認」を押す | GETだけを行う。更新要求は再送しない |
| ページを閉じる・アプリ再起動 | 通信の中止を依頼する。未完了要求は保存・再送せず、次回一覧でサーバー状態を取得する |

GETで読めるのはその時点の状態で、元のPUTが失敗した証明ではない。HTTPの中止もサーバー保存の取り消しを保証しない。閉じる直前や応答不明時の変更を次回へ保証する設計ではない。

## 一覧取得

- PageのonMountedからVM.initializeを呼ぶ。初回は20件。取得中はスケルトンを表示する。
- 末尾の240px手前から追加取得する。読み込みが間に合わない場合は末尾の取得ボタンがローディング表示になる。手動でも取得できる。
- フィルター変更でサーバーから取り直す。続きにも同じフィルター条件を適用する。
- 初回・更新・追加の失敗は再試行ボタン。更新・追加の失敗では既存記事を残す。
- フィルター変更前の応答は破棄する。保存後に届く古い一覧応答で確定した状態を戻さない。
- 画面内だけの状態はVMが持つ。続き位置は通常変数で、画面への変更通知を必要としない。

## 保存基盤と移行範囲

一覧のIndexedDBキュー、Web Locks、接続復帰時の自動再送、操作IDの結果照会、起動時同期、Pinia Storeを削除した。未使用のpinia・idb・fake-indexeddb依存も削除した。旧ブラウザ内の記録は読み込みも送信もせず、自動削除もしない。サーバーの旧操作表・マイグレーションも保持する。

仕分けAPIのbatchId・revision・結果保存・重複防止は変更しない。仕分け画面と端末保存は後続Issueで実装し、今回の一覧へ混ぜない。
