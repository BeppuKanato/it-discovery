技術選定とコード配置は[技術構成](architecture.md)、採用したカード配置は[画面構成の参照](ui-reference.md)を参照する。以下の操作ルールは技術選定だけでは変更しない。

記事の識別・日時・ページング・収集先・初期設定・収集と保持の保存単位は[記事データと収集の方針](data-policy.md)に具体化した（Issue #3）。

## 設計の範囲

記事の収集、共通データへの変換、仕分け、気になる登録、一覧、既読、ピン止め、記事の保持・削除を対象とする。推薦アルゴリズム・類似度・興味の推定は対象外とする。

見送りだけで「興味がない」と判定しない。見送りを学習用の長期履歴として残すことも、現段階では要件に含めない。

## 用語

| 用語 | 意味 |
|---|---|
| 記事 | アプリが扱う情報の一件。技術記事、更新情報、動画、Podcast、リリース情報を含む |
| 出典元 | 記事の掲載元。表示名と、同一記事判定に使う取得元の識別情報は区別する |
| 収集 | サーバーが外部のRSS・Atom・APIなどから情報を取り込み、DBに追加・更新する処理 |
| 一覧の更新 | アプリがDBの最新内容を読み直す処理。外部の情報源への収集要求ではない |
| 仕分け | Tinder型のカードUIで、一件ずつ「気になる」登録または見送りを判断するフェーズ |
| 一回の仕分け | 開始から終了確定までの、最大10件の仕分け |
| 気になる | 後で確認したい記事として登録されている状態。「お気に入り」と同じ意味で話していたものを、この表記に統一する |
| 見送り | その回では選ばず次へ進む判断。削除・既読・永続的な除外とは異なる |
| 取り消し | その回の直前の仕分け判断を戻し、その記事のカードに戻る操作。繰り返してさかのぼれる |
| 既読 | 外部の掲載ページを開いた状態。読み終えたことを意味しない |
| ピン止め | 自動削除から記事を保護する、気になる登録とは独立した状態 |
| 全記事一覧 | 現在DBに保持している記事の一覧。過去に取得して削除した記事や、外部サイトの全記事は含まない |
| 気になる一覧 | 現在「気になる」に登録されている記事の一覧 |
| 公開日時 | 掲載元が提供する公開日時。取得できない記事もある |
| 取得日時 | 最初にDBへ取り込んだ日時。再取得では変更しない。保持期限・並び順・未読の削除順に使う |
| 掲載元の更新日時 | 掲載元から公開日時と別に取得できる場合の更新日時 |
| 最後に開いた日時 | 元記事を最後に開いた日時。既読記事の削除順に使う |

## 表示・記事を開く

| ID | ルール |
|---|---|
| UI-01 | 日本語・スマホ向けを基本とする |
| UI-02 | サムネイル領域内に中央揃えのタイトル、小さな説明、出典アイコン・サイト名を配置する。日付などは下に表示する |
| UI-03 | 著者の表示は必須にしない。説明・公開日が取得できなければ、その項目を表示しない |
| UI-04 | 仕分けと各一覧の表示順は、取得日時が新しい順とする |
| UI-05 | カード・各一覧の記事をタップすると、元の外部サイトを直接開く。アプリ内の詳細画面は設けない |
| UI-06 | 登録・解除・ピン止め用の操作は、記事を開く操作と区別する |
| READ-01 | 外部タブの作成と元記事への遷移依頼を受け付けた時点で既読にする。タブ作成拒否・URL不正・遷移依頼の例外を検知した場合は既読にしない。外部サイトの通信エラー・本文表示の成否・読了は判定しない（[判定方法](operation-policy.md#合意済み外部記事と既読)） |
| READ-02 | 仕分けから元記事を開いても「気になる」には自動登録しない |
| READ-03 | 外部サイトから戻ったときは、同じ記事のカードを表示する。既読になったことだけを理由に自動で次へ進めない |
| READ-04 | 既読・未読を手動で切り替える機能は、今回のユースケースに含めない |

既読になった表示中のカードを残すことと、次の仕分けの対象から既読を除外することは別のルールである。

## 仕分け

| ID | ルール |
|---|---|
| SORT-01 | 仕分け開始時にDBから対象を選ぶ。外部情報源への収集とは別の処理とする |
| SORT-02 | 対象は、未読・気になる未登録・ピン止めなしの記事とする。別の永続的な「仕分け済み」状態は必須にしない |
| SORT-03 | 一回は最大10件とする。対象が1〜9件でも、その件数で開始できる。0件のときだけ開始をロックする |
| SORT-04 | 対象は取得日時が新しい順に選ぶ |
| SORT-05 | 右スワイプで「気になる」の仮の登録を追加し、次のカードへ進む。左スワイプで見送り、次のカードへ進む。サーバー通信の完了を待たない |
| SORT-06 | 見送った記事は同じ回では再表示しない。ただし、取り消してその記事へ戻る場合は除く |
| SORT-07 | 次の回では見送り記事を特別扱いせず、対象条件と取得日時順に従って再び選べる |
| SORT-08 | 見送り・現在位置・取り消し履歴はその回だけ一時的に保持する。アプリ終了後の回の再開は行わない。未送信の気になる登録結果は端末に残す |
| SORT-09 | 判断履歴のある範囲で「戻す」を繰り返してさかのぼれる。見送りまたは仮の気になる登録を手元で取り消し、その記事のカードに戻る。取り消した登録を送信対象から外す。サーバーへの解除要求は出さない |
| SORT-10 | 元記事を開く操作は、仕分け判断の取り消し対象に含めない |
| SORT-11 | 最後のカードの判断後に完了画面を表示しても、「仕分けを終了する」で終了確定するまでは戻せる |
| SORT-12 | 「仕分けを終了する」で最終的な気になる登録をまとめて送信する。保存成功後、その回の見送り・進行状況・取り消し履歴を破棄する。DBに保存した気になる・既読・ピン止めは残す。登録対象がなければ登録通信は不要 |
| SORT-13 | 完了画面の表示だけでは送信しない。仕分け中の登録・見送り・取り消しは手元で処理する。見送り・判断履歴をサーバーへ送信しない |
| SORT-14 | 仮の気になる登録結果は、変更のたびに端末へ非同期で保存する。画面の進行は端末保存の完了を待たない。取り消しも保存結果に反映する |
| SORT-15 | 途中で閉じた場合、次の起動時に端末に残っている気になる登録結果をまとめて送信する。前の回の位置・見送り・取り消し履歴は復元しない |
| SORT-16 | サーバーへの保存成功を確認した送信結果だけを端末から削除する。通信失敗・応答不明では結果を残し、再送できるようにする |
| SORT-17 | 同じ登録を再送しても、サーバーで同じ記事を二重登録しない |
| SORT-18 | 起動時に端末の未送信登録があれば、サーバーへの保存成功を確認するまで一覧・仕分けの通常操作を待機させる。一時的な通信失敗は間隔を空けて再試行する。利用者は再試行を続けるかアプリを終了するかを選べ、終了しても未送信結果を消さない |
| SORT-20 | 仕分け中の一覧移動は設けない。途中でも「仕分けを終了する」で判断済み結果を確定する。送信開始後は判断・戻すを停止する |
| SORT-21 | 外部から戻った既読カードは「次へ」で進む。左右の仕分け判断は行わず、最大10件のうち1件として数える。次への進行も戻せるが既読は戻さない |
| SORT-22 | 開始時のカード情報と順序を固定する。途中の収集・更新を差し込まず、削除済みカードの登録は再作成せず失敗を知らせる |
| SORT-23 | 端末保存失敗時は判断・戻すを停止し、手元の最新結果を保って再試行または終了を選べる。未保存のまま終了すると失われる変更を知らせる |
| SORT-24 | 日次判定を端末ごとに日本時間の日付で保存する。対象0件でもその日は自動再開しない。取得失敗では日次判定を確定しない。手動開始は可能 |
| SORT-19 | 毎日の初回起動時に対象があれば最大10件の仕分けを自動開始する。日付は日本時間の午前0時で区切る。未送信登録の同期があれば完了後に判定する。その後も自由に仕分けを開始でき、収集完了では自動開始しない |

履歴がなければ戻すボタンを無効にする。仕分け中の「気になる」は仮の判断であり、サーバーのDBへの保存は終了時または次の起動時に行う。仕分け中に端末へ保存する未送信結果と、その回の取り消し履歴は別の情報として扱う。

端末保存の完了前に強制終了した場合、最後の変更が残らない可能性はある。終了直前の送信だけには依存しない。端末の保存領域が消去された場合は未送信結果を復元できない。

例えば、Aを気になる登録 → Bを見送り → Cを表示中なら、一度戻すとBの見送りを取り消してBを表示する。さらに戻すとAの気になる登録を取り消してAを表示する。

見送りだけで記事が揃っていても、次の回の対象になれる。繰り返し同じ記事が出すぎる場合の調整は、利用を確認してから検討する。

## 気になる・ピン止め・一覧

| ID | ルール |
|---|---|
| LIST-01 | 気になる登録は、仕分け中と全記事一覧から行える。登録済みの記事は仕分け対象から外れる |
| LIST-02 | 一覧から気になる登録を解除できる。解除は見送りとは異なる |
| LIST-03 | 登録解除後、未読かつピン止めなしであれば、次の仕分けの対象になれる。既読なら対象にならない |
| LIST-04 | 全記事一覧では、見送り・気になる登録・既読・ピン止めの有無にかかわらず、保持中の記事を表示する |
| LIST-05 | 気になる一覧には、気になる登録されている記事を表示する。既読でも表示する |
| LIST-06 | 全記事一覧・気になる一覧は全件一括取得せず、初回は先頭の20件を取得し、下までスクロールしたら最大20件ずつ続きを追加取得する。取得日時の降順、同時刻はDB内の記事IDの降順。最後の記事の日時・IDをカーソルにする |
| LIST-07 | 下に引いて更新すると、先頭から最新の一覧を読み直し、追加取得の続き位置も更新する |
| LIST-08 | 続きがないときは追加取得を停止する。取得失敗で表示済みの記事を消さず、追加取得失敗で続き位置を進めない |
| LIST-09 | 一覧のピン・気になるは保存中を部分着色し、成功後に登録状態を確定する。同じ記事の変更ボタンは保存中に制限する |
| LIST-10 | 保存が拒否されたら元の登録表示を保ち、理由を通知する。気になる一覧の解除は成功後に記事を外す |
| LIST-11 | 応答不明は保存失敗と断定しない。ピン・気になるは現在状態を一度GETし、確認不能なら操作を止めて手動確認を案内する |
| LIST-13 | 一覧のピン・気になる・既読は永続保存・自動再送・起動時再送を行わない。既読は開いた表示を即時反映し、保存の失敗・結果不明を区別して手動再試行を案内する |
| LIST-12 | 同じ記事のピン・気になるの二重操作を保存中に防ぎ、古い応答で最新表示を戻さない。既読保存の応答から登録状態を変更しない |
| PIN-01 | ピン止めは気になる登録とは独立とし、どちらか一方だけの状態も持てる |
| PIN-02 | 一覧のサムネイル付近の左上にピンアイコンを置き、設定・解除できるようにする |
| PIN-03 | ピン止めされた記事は仕分け対象外とし、自動削除の対象からも外す |

仕分け画面にピン操作を設けるかは未確定。一覧でのピン操作は今回の要件に含む。

## 記事の収集・識別・更新

| ID | ルール |
|---|---|
| COLLECT-01 | サーバーで定期収集し、取得結果をDBの既存記事に追加・更新する。毎回全件を入れ替えない |
| COLLECT-02 | アプリ起動時と一覧を下に引いたときは、DBから最新の一覧を読み直す |
| COLLECT-03 | 起動・一覧更新のたびに外部情報源へ取得する構成にはしない。外部への手動収集要求は現段階では設けない |
| COLLECT-04 | 記事データと確定した登録状態の保存先はサーバー側のDBを基本とする。仕分けの未送信登録結果は端末にも一時保存する。サーバーDBはSQLite、端末保存はIndexedDB＋idb、バックエンドはCompute Engine上のDockerとする。フロント配信先・VMの具体構成は未確定 |
| COLLECT-05 | 毎日午前5時（Asia/Tokyo）に取得先ごとに最新側から最大50件を確認する。既存記事は更新し、新規記事だけ保持ルールに従って追加する。提供件数が少なければその範囲で扱う。取りこぼしは許容し、古い未取得分から追い続けない。時刻と件数は変更可能な設定にする |
| COLLECT-06 | 収集中なら次の実行はスキップする。一つの取得先が失敗しても他の取得先を続行し、失敗履歴をDBへ保存する機能は設けない。次の定期収集で再取得する |
| COLLECT-07 | 情報源・取得先はユーザーが設定できる。対応方式とデフォルト取得先はdata-policyに定める |
| ID-01 | 同一記事は取得元の識別情報＋記事IDで判定する。記事IDがない場合は取得元＋URLの完全一致で判定する。URLの正規化や取得元をまたぐ統合、記事IDの有無が変わる場合の特別な移行処理は設けない |
| ID-02 | タイトル・著者の完全一致は主な同一記事判定に使わない |
| UPDATE-01 | 同一記事を再取得した場合、新しい記事を重複追加せず、タイトル・説明・著者を更新する。本文の変更検出は行わない。説明・著者がなくなった場合はnullにする |
| UPDATE-02 | 公開日時と取得日時は別に持つ。掲載元の更新日時を取得できる場合は、公開日時と別に扱う |
| UPDATE-03 | 再取得時はURL・公開日時・掲載元の更新日時を維持する。アプリの表示順と保持期限は最初の取得日時を基準にする |
| UPDATE-04 | 記事が更新されても既読状態は維持する |

情報源ごとにRSS・Atom・APIなどの取得方法を選び、共通の記事データに揃える。対応方式・デフォルト取得先・保存単位は[data-policy](data-policy.md)に従う。

## 保持・削除・取得停止

| ID | ルール |
|---|---|
| KEEP-01 | 取得した記事を蓄積し、保持期限・記事件数の上限で自動削除する |
| KEEP-02 | 気になる登録またはピン止めされた記事は、保持期限・件数超過のどちらでも自動削除しない |
| KEEP-03 | 保持期限は取得日時を基準にする。保護されていない未読記事を期限による削除対象とし、既読記事は期限では削除しない |
| KEEP-04 | 件数超過時は、保護されていない未読記事を取得日時が古い順に削除する |
| KEEP-05 | 未読記事の削除後も超過していれば、保護されていない既読記事を、最後に開いた日時が古い順に削除する |
| KEEP-06 | 記事を削除すると既読記録も削除する。後で再取得されて未読として現れることは許容する |
| KEEP-07 | 気になる・ピン止めによる保護記事だけで上限に達した場合は、新しい記事の追加を停止する |
| KEEP-08 | 新規追加を停止中も、既存記事の更新は行う |
| KEEP-09 | 保護記事が減り上限に空きができれば、次の定期収集タイミングで新しい記事の追加を再開する |
| KEEP-10 | 保持期限の初期値は最初の取得日時から30日、全体の記事件数上限は10,000件。変更可能な設定にする。同時刻の削除順はDB内の記事IDの昇順 |

「追加停止」は新規記事をDBに追加しない意味であり、既存記事の更新まで止める意味ではない。更新を調べるための外部取得方法は、情報源ごとの設計で決める。

気になる・ピン止めを解除した記事は、保護がなくなれば通常の削除ルールに従う。公開日時ではなく取得日時が削除順の基準となる。

|---|---|---|
| OPEN-01 | 解決済み：取得日時 | 最初の取り込み時点で固定。再取得では変更しない（data-policy） |
| OPEN-02 | 解決済み | 仕分け中の一覧移動は設けず、途中終了で判断済み結果を確定する（SORT-20） |
| OPEN-03 | 解決済み | 同じカードへ戻り、既読カードは次へで進む。1件と数え、気になるを変更しない（SORT-21） |

| OPEN-06 | 解決済み：記事の識別 | 共通データの取得元＋記事ID、IDなしは取得元＋URL完全一致。正規化・ID有無の移行は設けない（data-policy） |

| OPEN-08 | 同時利用 | 複数端末や利用者・認証の扱い。現時点では確定していない |
| OPEN-09 | 解決済み | 一時失敗は再試行、保存失敗は操作停止、削除済み・不正要求などは別の解消手段を設ける（操作方針） |
| OPEN-10 | 解決済み：数値と同順 | 30日・10,000件、同時刻はDB内の記事IDで固定（data-policy） |
